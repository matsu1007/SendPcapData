# send_pcap

pcapファイル（Wiresharkでキャプチャしたログ）に記録されたパケットを、宛先を書き換えつつネットワークに再送信するツールです。

スクリプト内部の実装（各モードの処理の流れ、関数の役割、設計判断の理由）は [ARCHITECTURE.md](ARCHITECTURE.md) を参照してください。

## どのモードを使うか

| やりたいこと | 使うモード |
| --- | --- |
| pcapの内容をそのまま（または宛先だけ変えて）再送信したい | 基本モード |
| TCP上のファジングテストを再現したい（異常なのはペイロード＝アプリ層データ） | `--tcp-session` |
| TCP上のファジングテストを再現したい（異常なのはTCPヘッダ自体：フラグ/window/urgent pointer/予約ビット/seq・ack） | `--tcp-raw-session` |
| 上記のいずれかで、繰り返し送信による対象機のクラッシュ/再起動を再現したい | 各モードの `--until-disconnect` |

迷ったら、まず「異常なのはペイロードかヘッダか」で `--tcp-session` と `--tcp-raw-session` を切り分けてください。TCP以外（UDPなど）や、単純な再送信・宛先変更だけなら基本モードで十分です。

## 必要環境

- Python 3.x
- [Npcap](https://npcap.com/) （Windowsでパケット送受信するために必要。インストール時に "WinPcap API-compatible Mode" を有効にしてください）
- 管理者権限のPowerShell（`--tcp-session` 以外は生パケット送受信を行うため必要）

## セットアップ

```powershell
pip install -r requirements.txt
```

## 共通の準備: 送信先インターフェースを確認する

基本モードと `--tcp-raw-session` は、送信に使うNIC（インターフェース）を `-i` で指定する必要があります（`--tcp-session` は通常の`socket`接続を使うため不要です）。

まず、このツール（Npcap）から見えるインターフェース一覧を表示します。

```powershell
python send_pcap.py --list-ifaces
```

`\Device\NPF_{FCAD7E4A-B868-44F4-BFC2-732B933A8005}` のように、`{}` の中にGUIDが入った形式で一覧が表示されます。このGUIDだけでは名前が分からないので、Windows側のアダプター一覧と突き合わせます。

```powershell
Get-NetAdapter | Select-Object Name, Status, InterfaceDescription, InterfaceGuid | Format-List
```

実行すると、たとえば以下のように表示されます。

```
Name              : イーサネット
Status            : Up
InterfaceDescription : Realtek PCIe 2.5GbE Family Controller
InterfaceGuid     : {C901FF5F-BD84-44D9-94AB-E301EE99CDF2}

Name              : Wi-Fi
Status            : Disconnected
InterfaceDescription : MediaTek Wi-Fi 6E MT7922 (RZ616) 160MHz Wireless LAN Card
InterfaceGuid     : {A8A3ECB5-3A33-4C22-9289-489A85FBAB81}
```

`InterfaceGuid` の値（`{}` を含む）が `--list-ifaces` で表示された `\Device\NPF_{...}` のGUID部分とそのまま一致するので、対応する `Name` を確認できます。上記の例なら、`\Device\NPF_{C901FF5F-BD84-44D9-94AB-E301EE99CDF2}` が「イーサネット」（有線LAN）に対応します。

対象デバイスとの通信に使うインターフェースを選ぶ際のポイント：

- **`Status` が `Up`** のものだけが実際にケーブルが繋がっている（通信できる）候補です。`Disconnected` のものは除外してください。
- **`InterfaceDescription`** でおおよそ種類が分かります（例: `Realtek ... Controller` は有線Ethernet、`Wi-Fi` を含むものは無線、`Hyper-V Virtual Ethernet Adapter` や `vEthernet` はVM/WSL用の仮想アダプターなので、物理的にテスト対象機と繋がっているものではありません）。
- **接続先が複数の有線ポートがあって迷う場合**は、テスト対象機とのケーブルを一度抜き差しして、`Get-NetAdapter` を再実行し、`Status` が `Up`→`Disconnected`→`Up` と変化するアダプターを探すと確実です。

  ```powershell
  # ケーブルを抜いた直後に実行 → 該当アダプターだけ Disconnected になるはず
  Get-NetAdapter | Select-Object Name, Status
  ```

- IPアドレスで確認したい場合は、`Get-NetIPAddress -InterfaceAlias "イーサネット"` のように `Name` を指定すると、そのインターフェースに割り当てられたIPアドレスを確認できます。

特定できたら、`--list-ifaces` の出力からその `\Device\NPF_{...}` の文字列全体をコピーし、`-i` オプションにそのまま渡してください。

## 基本モード: 生パケットをそのまま再送信する

### 内容を確認する（送信しない）

実際に送信する前に、書き換え後の内容を確認できます。

```powershell
python send_pcap.py capture.pcap --dry-run
```

宛先を書き換えるオプションを付ければ、書き換え後の内容がそのまま表示されます。

```powershell
python send_pcap.py capture.pcap --dst-ip 192.168.1.50 --dst-port 8080 --dry-run
```

### 実際に送信する

管理者権限のPowerShellで実行してください。

```powershell
python send_pcap.py capture.pcap -i "\Device\NPF_{FCAD7E4A-B868-44F4-BFC2-732B933A8005}" --dst-ip 192.168.1.50 --dst-port 8080
```

### Device A → Device B の通信だけを再現する

デバイスAとBの間の通信を記録したpcapから、Device Aが送信したパケットだけを抽出して再送信できます。Device Aの送信には意図的な異常データが含まれることがあるため、宛先を書き換えない限りチェックサムなどは一切変更せず、元の内容をそのまま送信します。

```powershell
# Device A (10.0.0.1) が送信したパケットだけを、そのまま実機のDevice Bへ再送信
python send_pcap.py capture.pcap -i "\Device\NPF_{...}" --src-ip 10.0.0.1

# 送信先を別の検証機に向けつつ、異常データ（不正チェックサムなど）は維持したい場合
python send_pcap.py capture.pcap -i "\Device\NPF_{...}" --src-ip 10.0.0.1 --dst-ip 192.168.1.50 --keep-checksum
```

MACアドレスでしか送信元を区別できない場合（IPを持たないフレームなど）は `--src-mac` を使ってください。

### 基本モードの動作の仕組み

1. `PcapReader` でpcapファイルをストリーミング読み込みする。
2. `--src-ip` / `--src-mac` を指定した場合、送信元が一致しないパケットは読み飛ばす（Device Aの送信だけに絞り込む）。
3. `--dst-ip` / `--dst-port` / `--dst-mac` を指定した場合、該当レイヤー（Ethernet/IP/IPv6/TCP/UDP）の宛先フィールドを書き換える。
4. 宛先を書き換えた場合、影響を受けるチェックサム（IP/TCP/UDP）だけを削除し、送信時にscapyが自動再計算するようにする。`--keep-checksum` を指定すると、この再計算をせず元の値のまま送信する。
5. Ethernetヘッダを持つパケットは `sendp`（L2送信）、持たないパケットは `send`（L3送信）で送出する。

宛先を一切書き換えない場合（`--dst-*` を指定しない場合）は、チェックサムや長さも含めて元のpcapに記録された値がそのまま送信されます。これにより、Device Aが送信した「おかしなデータ」を含むパケットもそのまま再現できます。

## `--tcp-session`: ペイロードのファジングを再現する

pcapがTCP上でのファジングテストの記録で、**異常なのはアプリ層データ（ペイロード）** の場合に使います。生のTCPパケットをそのまま再送するだけでは、宛先のOSがseq/ack番号の不整合を検知してRSTを返したり、パケットを黙って無視したりして再現になりません。

`--tcp-session` を使うと、宛先へ**実際にTCP接続（3-wayハンドシェイク）を確立**し、Device Aが送信したペイロード（ファジングされたデータ本体）だけをそのコネクション上に元の順番のまま流します。ハンドシェイクやseq/ack番号の管理はOSのTCPスタックに任せるため、宛先アプリケーションには実際にファジングを行ったときと同じバイト列が届きます。SYN/ACK/FINのみの制御パケットは自動的にスキップされます。

```powershell
# Device A (10.0.0.1) が送信したファジングデータを、実機Bのポート9999へ再現
python send_pcap.py capture.pcap --tcp-session --src-ip 10.0.0.1 --dst-ip 192.168.1.50 --dst-port 9999
```

このモードは通常の`socket`接続を使うため、**管理者権限やNpcapのインターフェース指定（`-i`）は不要**です。`--dst-mac` や `--keep-checksum` はこのモードでは意味を持ちません（OSが正しいヘッダを都度生成するため）。

pcapに複数のTCP接続が記録されている場合は、`--src-port` で元の送信元ポートを指定して対象の接続を絞り込んでください。

```powershell
python send_pcap.py capture.pcap --tcp-session --src-ip 10.0.0.1 --src-port 40000 --dst-ip 192.168.1.50 --dst-port 9999
```

### 繰り返し送信によるクラッシュ/再起動を再現する（`--until-disconnect`）

「同じデータを繰り返し送るとデバイスが再起動する」現象を再現したい場合に使います。pcapにすでに繰り返し送信の履歴が記録されているなら、その全ペイロード列を1つのTCP接続上で**何度もループ送信し続け**、接続が切断された時点（デバイスのクラッシュ/再起動でRSTが返る、または無応答になる）で自動的に停止し、何周目・何件目で切断されたかと累計送信数を表示します。

```powershell
python send_pcap.py capture.pcap --tcp-session --until-disconnect --src-ip 10.0.0.1 --dst-ip 192.168.1.50 --dst-port 9999
```

- `--loop` は使いません（`--until-disconnect` は無限に繰り返すため）。`--dry-run` との併用もできません（実接続なしでは切断を検知できないため）。
- `--timeout`（デフォルト5秒）で、応答が無くなったデバイスをどのくらいの時間で「切断」とみなすかを調整できます。デバイスがハングして応答しなくなるだけでRSTを返さない場合、切断の検知にこのタイムアウトが必要です。
- TCPは送信側バッファに乗った時点で`sendall`が成功扱いになるため、実際の切断（クラッシュのタイミング）より少し遅れて検知されることがあります（OSのTCPスタックの仕様によるもので、ツール側では回避できません）。目安として捉えてください。

## `--tcp-raw-session`: TCPヘッダのファジングを再現する

pcapがTCP上でのファジングテストの記録で、**異常なのはTCPヘッダ自体**（フラグの異常な組み合わせ、window/urgent pointer/予約ビットの値、seq/ack番号自体の不整合など）で、ペイロードは空、という場合に使います。`--tcp-session`（通常のsocket）ではTCPフラグやwindow/urgent pointerを直接操作できず対応できません。また対象デバイスはそれらの異常パケットを**実際に確立されたセッションのseq/ackに整合していないと受理しません**。

`--tcp-raw-session` は、生パケットで自前のTCPハンドシェイク（SYN→SYN-ACK→ACK）を実際に組み立てて宛先と本物のセッションを確立し、Device Aが送信した異常パケットを、そのセッションの新しいISN（初期seq番号）に合わせてseq/ackだけを読み替えて送信します。TCPフラグ・window・urgent pointer・予約ビットなど異常値そのものは元のまま送出されます。ファジングデータは必ずハンドシェイク成立後に送信される前提のため、pcap中でハンドシェイクを完了させるだけの素のACK（3-way handshakeの3番目のパケット）は自動的に対象から除外されます。

**複数接続（テストケースごとにポートを変える）に対応しています。** 元のファジングテストがテストケースごとに送信元ポートを変えて新しいTCP接続を張り直す作りである場合、pcapからDevice Aが張った接続をすべて出現順に抽出します。宛先ポート（対象機側）は全接続で共通という前提です。

**接続同士の重なりも再現します。** 前の接続が閉じきる前に次の接続が始まっている（同時に複数の接続がオープンになっている）場合、各接続をスレッドで並行に実行し、`--realtime` 指定時は元のpcapでの最初のSYNからの相対タイミング通りに、それぞれの接続の開始をずらします（`--interval` 指定時は前の接続の開始からその間隔で、どちらも指定が無ければ全接続をほぼ同時に開始します）。これにより、単純に1件ずつ順番に処理するだけでは再現できない「複数接続が同時に張られている状態」そのものを再現できます。

### 基本の使い方

1. **pcapを確認する。** `--dry-run` で、pcap内に見つかった接続の件数・各接続の再現対象パケット（フラグ/window/urgent pointer/予約ビットなどの異常値）を確認します。`--spoof-ip` の決め方は次項を参照してください。

   全接続のファジング内容（フラグ/window/urgent pointer/予約ビット/ペイロード）が同一の場合は、接続数ぶん同じ内容を繰り返し表示する代わりに、代表1件分の内容と、使用される送信元ポートの一覧（件数が多い場合は先頭・末尾のみ）をまとめて表示します。内容が接続ごとに異なる場合は、これまで通り接続ごとに詳細を表示します。

   ```powershell
   python send_pcap.py capture.pcap --tcp-raw-session --src-ip 10.0.0.1 --dst-ip 192.168.1.50 --spoof-ip 10.0.0.1 --dry-run
   ```

2. **管理者権限のPowerShellで実行する。**

   ```powershell
   # 宛先ポートを省略した場合、pcap記録時にDevice Bが使っていたポートがそのまま使われる
   python send_pcap.py capture.pcap --tcp-raw-session -i "\Device\NPF_{...}" --src-ip 10.0.0.1 --dst-ip 192.168.1.50 --spoof-ip 10.0.0.1
   ```

- `-i`（インターフェース）・`--dst-ip`・`--spoof-ip` は必須です。
- `--local-port` を指定すると、**すべての接続**でその1つのポートを強制的に使います。通常は省略して、各接続ごとに元のpcapで使われていた送信元ポートをそのまま再利用してください。
- `--src-port` を指定すると、その送信元ポートの接続1件だけに絞り込んで再現します（特定のテストケースだけ試したい場合に使用）。
- `--dst-port` は省略可能です。省略した場合、pcap記録時にDevice Bが使っていたポート（全接続で共通）がそのまま使われます。検証機のポートが元と違う場合のみ指定してください。
- ハンドシェイク後にパケットが1件も無い接続（SYNだけで応答が無いなど）は再現対象から自動的に除外されます。

### `--realtime`（タイミングの再現）について

`--realtime` を付けると、元のpcapに記録されたタイミングを**2つのレベル**でできるだけ忠実に再現します。付けない場合は、どちらもタイミングを気にせず即座に送信します（高速だが、元のpcapとはタイミングが大きく変わります）。

```powershell
python send_pcap.py capture.pcap --tcp-raw-session --realtime -i "\Device\NPF_{...}" --src-ip 10.0.0.1 --dst-ip 192.168.1.50 --spoof-ip 10.0.0.1
```

1. **接続と接続の間隔（いつ次のSYNを送るか）**

   各接続は「元のpcapで最初のSYNが記録された時刻から、その接続のSYNが記録された時刻までの経過時間」だけ待ってから開始されます。たとえば元のpcapで1件目のSYNの0.15秒後に2件目のSYNが記録されていれば、こちらの再現でも1件目の接続を開始してから0.15秒後に2件目の接続を開始します。前の接続がまだ終わっていなければ（＝元のpcapで接続同士が重なっていれば）、そのまま並行して重なります（詳しくは前述の「接続同士の重なりも再現します」を参照）。

   - `--realtime` の代わりに `--interval` を指定すると、経過時間を無視して「前の接続の開始から固定N秒後」に次の接続を開始します。
   - どちらも指定しない場合、全接続がほぼ同時に開始されます。

2. **1つの接続の中でのパケット間隔（ハンドシェイク後、いつファジングパケットやRSTを送るか）**

   ハンドシェイクを完了してからファジングパケットを送るまで、そしてファジングパケットを送ってから（応答が無く）RSTを送るまでの間隔も、元のpcapに記録された経過時間の通りに `time.sleep()` で待ってから送信します。「対象機の応答を待ってタイムアウトしてからRSTを送る」までの間隔も、このタイミングとして自然に再現されます。

   - こちらも `--realtime` の代わりに `--interval` を指定すると、記録された経過時間を無視して固定N秒の間隔になります。
   - どちらも指定しない場合、ハンドシェイク完了後、ファジングパケットとRSTがほぼ間を置かず連続で送信されます。

**精度について。** ハンドシェイクの応答待ち（`sr1()`のラウンドトリップ時間）やスレッド起動のオーバーヘッドがあるため、実際の送信タイミングは元のpcapの記録と完全には一致せず、数ms〜数十ms程度のずれが生じます。対象機の挙動がミリ秒単位のシビアなタイミングに依存する場合は、この程度のずれで再現性に影響が出る可能性があります。

### `--spoof-ip`（送信元IPの偽装）について

自前でSYNを生パケットとして送ると、実際のWindows機のIPアドレスを使った場合、Windows自身のTCP/IPスタックはその接続を認識していないため、対象デバイスからのSYN-ACK応答を見て「身に覚えのないパケット」と判断し、勝手にRSTを送り返してセッションを壊してしまいます。

これを避けるため、`--spoof-ip` で**このWindows機に割り当てられていない、対象と同じサブネット上の未使用IPアドレス**を指定してください。送信元をそのIPだと名乗ることで、対象からのSYN-ACKはWindows自身には「自分宛ではないパケット」として無視され、RSTが送られなくなります（ファイアウォールの設定変更は不要です）。対象機は偽装IPのMACアドレスをARPで問い合わせてきますが、このツールが裏で自動的に応答するので追加作業は不要です。

**推奨: Device Aの元のIPをそのまま使う。** テスト対象機とWindows機を有線で直結し、間にハブなどの中継器があるだけで他のデバイスが存在しない構成であれば、IPアドレスの衝突を気にする必要はありません。この場合、`--spoof-ip` には**pcap記録時のDevice A自身のIPアドレス**（`--src-ip` と同じ値）をそのまま指定するのが、最も忠実な再現になり、かつ最も単純です（上記の例はこの前提です）。ハブはEthernetフレームをそのまま中継するだけなので、ARP自動応答にも影響しません。

（他のデバイスも同じネットワークに接続されている環境では、Device Aがオフラインであることを確認するか、誰も使っていない別のIPアドレスを選んでください。）

対象がSYN-ACKを返さない場合は、`--spoof-ip` が対象と同じサブネット上の本当に未使用のIPになっているか、`--dst-ip`/`--dst-port` が正しいかを確認してください。

### 対象機の応答ログを使ったクラッシュ地点の把握

pcapに対象機（Device B）からの応答も記録されている場合、`--dry-run` は追加の情報を表示します。

- 各ファジングパケットの直後に、元のpcapで実際にDevice Bが返した応答（flags/seq/ack/window、あれば応答内容も）を `-> Device Bの応答（元pcap記録時）:` として並べて表示します。応答が無ければ「なし」と表示されます。
- 元のpcap全体から、**何件目の接続までは応答があり、何件目以降は応答が途絶えたか**を自動検出して先頭にまとめて表示します（応答が途絶えた地点が、クラッシュ/再起動が発生したと推測される箇所です）。ハンドシェイクのSYN-ACKすら返ってこなかった接続も「応答なし」として扱われます。

```
元のpcapでは、7件目（ポート50007）の接続までは対象機からの応答が確認できましたが、8件目以降（残り3件）の接続では応答が確認できませんでした（この時点でクラッシュ/再起動した可能性があります）
```

これは元のpcapの記録内容から導いた参考情報であり、実際に`--until-disconnect`で再現したときに同じ件数でクラッシュするとは限りません（対象機の状態や環境によって変動しえます）が、再現できたかどうかを判断する目安になります。

### 繰り返し送信によるクラッシュ/再起動を再現する手順

「ポートを変えながら接続を次々張り、それを何度も繰り返すと対象が再起動する」現象を再現する手順です。

1. 上記の「基本の使い方」の手順1（`--dry-run`）で、pcap内の接続件数と（あれば）クラッシュ推定地点を確認する。
2. `--until-disconnect` を付けて、管理者権限のPowerShellで実行する。抽出した全接続を（前述の通り、必要なら重なりを再現しながら並行に）1周ぶん再現する処理を、最初から繰り返します。**1周（全接続を送信し終えるたび）**に（生パケットとは別の）通常のsocket接続で対象への疎通を確認し、応答が無くなった時点で「クラッシュ/再起動」と判断して自動的に停止します。

   ```powershell
   python send_pcap.py capture.pcap --tcp-raw-session --until-disconnect -i "\Device\NPF_{...}" --src-ip 10.0.0.1 --dst-ip 192.168.1.50 --spoof-ip 10.0.0.1
   ```

3. 停止時に表示される「何周目で止まったか」を確認する。対象を復旧させてから再実行すれば、同じ再現を繰り返せます。

補足:

- タイミングを元のpcapに近づけたい場合は `--realtime` を付けてください（詳しくは前述の「`--realtime`（タイミングの再現）について」を参照）。
- `--timeout`（デフォルト5秒）で、生存確認1回あたりの待ち時間を調整できます。対象の応答が遅い場合は長めに設定してください。
- 複数接続を並行に扱う都合上、コンソールのログは接続ごとの出力が入り混じって表示されることがあります（`[1周目 2/5]` のような接続番号のプレフィックスで見分けられます）。
- `--dry-run` と `--until-disconnect` は併用できません（実接続なしでは生存確認ができないため）。

## オプション一覧

### 共通

| オプション | 説明 |
| --- | --- |
| `pcap` | 読み込むpcapファイルのパス（位置引数） |
| `--src-ip` | この送信元IPのパケットだけを対象にする（Device Aの送信のみ抽出する場合に指定） |
| `--src-mac` | この送信元MACのパケットだけを対象にする（Device Aの送信のみ抽出する場合に指定） |
| `--src-port` | この送信元ポートのパケットだけを対象にする（複数TCP接続を区別する場合など） |
| `--dst-ip` | 宛先IPアドレス。基本モードでは書き換え先、`--tcp-session`/`--tcp-raw-session` では接続先として必須 |
| `--dst-port` | 宛先ポート。基本モード・`--tcp-session` では接続先として必須。`--tcp-raw-session` では省略可（省略時はpcap記録時のポートを再利用） |
| `--until-disconnect` | `--tcp-session`/`--tcp-raw-session`専用。同じセッション上でペイロード/パケット列を繰り返し送り続け、対象が応答しなくなるまで継続する（クラッシュ/再起動の再現向け） |
| `--timeout` | `--tcp-session`/`--tcp-raw-session`専用。接続・送信のタイムアウト秒。デフォルト5.0 |
| `--interval` | パケット間の固定送信間隔（秒）。デフォルト0（間隔なしで連続送信） |
| `--realtime` | pcap記録時のタイムスタンプ間隔を再現して送信する（`--interval` より優先） |
| `--dry-run` | 送信せず、書き換え後の内容（`--tcp-session`時は送信予定のペイロード、`--tcp-raw-session`時は復元した元セッション情報）を表示するだけ |
| `--list-ifaces` | 利用可能なインターフェース一覧を表示して終了 |

### 基本モード専用

| オプション | 説明 |
| --- | --- |
| `-i`, `--iface` | 送信に使うネットワークインターフェース名（`--list-ifaces` で確認） |
| `--dst-mac` | 宛先MACアドレスを書き換える場合に指定 |
| `--keep-checksum` | 宛先を書き換えてもチェックサムは元のpcapの値のまま送信する |
| `--loop` | pcap全体を繰り返す回数。デフォルト1 |

### `--tcp-session` 専用

| オプション | 説明 |
| --- | --- |
| `--tcp-session` | このモードを有効にする |

### `--tcp-raw-session` 専用

| オプション | 説明 |
| --- | --- |
| `--tcp-raw-session` | このモードを有効にする |
| `-i`, `--iface` | 送信に使うネットワークインターフェース名（必須） |
| `--spoof-ip` | 必須。送信元として名乗るIP（このWindows機に割り当てられていない、対象と同じサブネット上の未使用IP）。Windows自身のRST送出を防ぐために使う |
| `--local-port` | すべての接続で使うローカルポートを強制指定する。省略時は各接続とも元のpcapで使われていた送信元ポートをそれぞれ再利用する |

## 注意事項

- 送信先ネットワークへの影響を十分確認したうえで実行してください（意図しない宛先への大量送信はネットワーク負荷やセキュリティインシデントの原因になります）。
- 生パケット送信（基本モード・`--tcp-raw-session`）は、管理者権限が無いと失敗します。
